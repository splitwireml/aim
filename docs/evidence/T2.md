## 1. Conversation identity (A1, A5)

**Zero-query experiment** (`/tmp/aim-t2/ident.mjs`). Each case opens a new tab on `search?udm=50&…` without `q`, waits 7 s, reads the state and closes the tab. OIL and LFP are two existing threads.

| Case | Parameters | Result |
|---|---|---|
| A | OIL `mstk` + OIL `mtid` | OIL thread, 1 turn, input visible; `mstk` rewritten |
| B | OIL `mtid` only | no thread, no turns, no input |
| C | OIL `mstk` only | OIL thread, input visible |
| D | OIL `mstk` + LFP `mtid` | **OIL** (URL `mtid` rewritten to OIL) |
| E | LFP `mstk` + OIL `mtid` | **LFP** thread (2 turns) |
| F | OIL `mstk` + provisional (early session-thread) `mtid` | OIL |
| G | invalid `mstk` + OIL `mtid` | no thread, no turns, no input |

Findings:
- `mstk` is the identity. `mtid` is not used to select the thread: Google rewrites it to the thread `mstk` resolves to. After load, the URL `mtid`, the highlighted history entry and `data-session-thread-id` all equal the resolved thread id.
- `mstk` changes on every reload and on most turns. Older `mstk` values keep working (A used a value from before earlier reopens; the stored `mstk` restored the thread after the Chrome restart).
- The stored URL is `search?udm=50&mstk=…&mtid=…&csuir=1`, without `q`, so reopening never submits a prompt.

**When the URL appears.** Times are from sending the first turn:

| Run | `data-session-thread-id` | `mstk` in URL | footer | final `mtid` |
|---|---|---|---|---|
| s1 (prior worker) | 0.6 s | 0.6 s | 7.8 s | 10.6 s |
| s2 (Q1) | 0.7 s | 3.2 s, **same poll as footer** | 3.2 s | 3.6 s |
| s8 (Q8) | 0.6 s | 10.8 s, **same poll as footer** | 10.8 s | 11.4 s |
| s10 (Q9) | 0.7 s | 5.4 s, **same poll as footer** | 5.4 s | 6.1 s |

- The early `data-session-thread-id` is not the final thread id, and on its own it does not open the thread (like case B).
- A URL with `mstk` plus that early id is **provisional**. It restores the right thread, because `mstk` decides. Since its `mtid` never matches, the CLI stores `firstPrompt` with it, and `checkWritable` compares the restored thread's first query instead of the id. After a writable resume, the stored URL is replaced by the final URL and `firstPrompt` is dropped (seen in s3 and s9).
- **A5: not established.** Only 1 of 4 first turns exposed `mstk` before completion. Follow-up turns do not matter: the thread already has a stored URL by then.

**Result: pass for identity. A5 is recorded as false or unreliable.**

## 4. Quit during generation (FR-4.2, FR-4.3)

- Run s10 (Q9, final code): `aim --name t2-early`, "What are the main steps in making a traditional French baguette?". `/quit` came 1.7 s after send; no `mstk` yet. Output: `[this conversation is not saved yet]`, and no `t2-early` entry was written. Google kept generating: the footer appeared at 5.4 s and the final `mtid` at 6.1 s. The thread exists only in Google's AI Mode history.
- Run s8 (Q8): the URL first appeared at completion, 10.8 s. `/quit` at 11.4 s printed `[session t2-long saved]`. Run s9 then ran `aim -r t2-long` after the timeout-and-quit: writable, with the full answer present in the restored thread.
- Run s2: the provisional URL was saved and `/quit` came while the CLI turn was pending. It resumed correctly in s3 (check 2).
- Not observed: a save made strictly before the footer, then resumed. Only s1 exposed `mstk` early, and s1 hit the save bug below.

Bug found and fixed. In s1, a `/quit` during generation printed "not saved yet" even though `mstk` was present: the per-turn ticker's in-flight save turned quit's save into a no-op. Saves are now serialized.

**Result: pass on the warning path and on save-at-completion.** A save before completion is unproven because of A5.

## 5. Ctrl-C/timeout while Google is generating (FR-3.6, FR-3.8)

**Ctrl-C**, runs s3 and s7:
- s3: Q3 (a long two-day baking schedule) was sent, then SIGINT 3.0 s later → `[stopped waiting locally — Google may still be answering; prompts resume when it is idle]`.
  - 0.3 s later, "Can rye flour be used for the starter?" → `[Google is still answering — wait or /open]`. The watcher showed 3 turns (no submission), and Google's footer appeared about 5 s later (generation was not cancelled).
  - 45 s later the same text was sent again: reconcile returned idle and the Q3 answer was printed (FR-3.8 re-extract), then the prompt was submitted. The watcher showed **4 turns**, so the rejected copy was never queued or resent.
- s7, after the Chrome restart: same pattern. Q6 plus SIGINT at 3.0 s; "Short version please." rejected at 3.3 s; the footer came about 3.5 s later. 45 s later the same text was accepted and printed at 4.5 s. **7 turns** in total, no duplicate.

**Timeout**, run s8 with `AIM_TURN_TIMEOUT_MS=2500`, Q8 (history of rye bread):
- `[incomplete — run /open]` at 2.5 s.
- "Is pumpernickel a rye bread?" → `[Google is still answering — wait or /open]`.
- Resuming later (s9) showed the thread with **1 turn**, so the rejected prompt was never submitted.

Before the fix, the save poll stopped at timeout or Ctrl-C, so a URL appearing later was saved only at `/quit`. The poll now runs for the whole process (final code, s9/s10).

Local cancellation is not remote cancellation: in every interrupted run, Google finished the answer after aim stopped waiting.

**Result: pass.** The generating signal is "last turn has no visible footer". A turn that never gets a footer (an error answer) would stay in recovery; not observed.

## 6. Wrong-thread or fresh-chat redirect on resume (FR-4.5)

Zero-query runs s6 and s6b used a scratch index. For each entry: `aim -r <name>`; after 17 s, type "This prompt must not be submitted"; then `/quit`.

| Entry | Stored URL | Google showed | CLI |
|---|---|---|---|
| wrong-thread | LFP `mstk` + OIL `mtid` | LFP thread | `[session cannot be continued in Google — see AI Mode history, /open]` at 3.3 s; the prompt got the same message |
| fresh-redirect | invalid `mstk` + OIL `mtid` | no thread, no input | same message after the 15 s `checkWritable` timeout; the prompt got the same message |
| wrong-first | bread `mstk` + provisional `mtid` + `firstPrompt` "A different first question" | bread thread | same message at 2.6 s; the prompt got the same message |

- The watcher showed unchanged turn counts and no `q` navigation, so nothing was submitted.
- **Bug found and fixed.** On the first run (s6), `/quit` saved the wrong page's URL over the entry (wrong-thread was rewritten to the LFP URL, and wrong-first lost `firstPrompt`), violating FR-4.4. A resumed session is now saved only after `checkWritable` returns writable. Re-run s6b: `shasum` of the index was identical before and after.

**Result: pass.**
