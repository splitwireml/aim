## Proven findings at the base revision

### 1. Saved conversation cannot pass restoration validation — M0 blocker

The live operator created and saved a conversation only after the address-bar `mtid` equaled the highlighted history id. An immediate `aim -c` showed both expected user queries byte-for-byte and a visible follow-up input. Google had changed both `mstk` and `mtid`; the new address-bar `mtid` still equaled the new highlighted id, but differed from the stored `mtid`. `checkWritable` therefore returned `wrong_conversation`. Distinct history entries with the same title were observed, so matching text does not establish whether this is the original conversation or a copy.

Earlier evidence in `T2.md` established that `mstk` selects a conversation and is rewritten on reload, while Google rewrites `mtid` to the resolved thread. The new observations invalidate the previous assumption that a saved final `mtid` will match the result of reopening its URL.

No stable native history identifier was found. Transcript matching was deliberately rejected as an identity substitute. The safe runtime fixes below preserve fail-closed behavior, so they do not solve this blocker.

### 2. Sign-in recovery could bypass strict identity

At `bin/aim.js` base lines 101–119, startup attention entered recovery with saving disabled. The next prompt called only `reconcile`; a fresh or different completed conversation reports `idle`, after which the CLI printed its latest answer and called `send` without re-running `checkWritable` against the saved session.

A deterministic fake-browser reproduction showed:

```text
[needs attention — run /open]
STUB sent must not be sent
```

The saved index remained protected only because `canSave` was still false; submission and output attribution were not protected.

### 3. Follow-ups were not identity-gated and the ticker could replace the saved URL

SRS FR-3.3 requires every follow-up to pass `checkWritable(page, storedUrl)`. The base CLI called it only once during startup. After a valid resume, changing the tab to another conversation allowed the next prompt to be sent there. The 250 ms save ticker could also replace the session entry because `conversationUrl` checked only that the address-bar and highlighted ids agreed with each other, not with the saved session.

### 4. An unfinished restored turn was treated as writable

`checkWritable` accepted matching ids plus a visible input without inspecting the last turn's completion footer. On restart, a matching thread with `signal: false` accepted a new prompt instead of entering recovery. `reconcile` already had the required generating/idle distinction; startup did not call it.

## Review of the bounded fixes

The working changes address findings 2–4 without weakening the unresolved cross-restart identity rule:

- `conversationUrl(page, expectedUrl)` permits a refreshed URL only when its confirmed `mtid` still equals the expected thread. A changed confirmed thread cannot overwrite the session entry.
- Every saved-session prompt passes `checkWritable` immediately before `send`.
- Recovery revalidates identity before extracting or printing the latest answer.
- A successful post-attention recheck enables saving, updates `lastUsedAt` and `last`, persists the session, and only then prints or submits.
- A successful startup restore calls `reconcile`; an unfinished last turn enters recoverable `generating` state and rejects prompts until idle.

The added deterministic cases cover accounts/consent attention, Ctrl-C recovery without replay, attention resolving to a wrong conversation, successful sign-in recovery metadata, tab drift plus ticker protection, unfinished resume, and same-thread URL-token refresh.
