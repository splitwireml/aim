- address-bar thread id = highlighted history id = stored thread id;

- two expected user turns were present;
- follow-up input was visible.

Each reopened tab also settled and remained stable for more than 30 seconds, but showed a different identity:

- reopened address-bar thread id = reopened highlighted history id;
- reopened thread id != stored thread id;
- reopened `mstk` != stored `mstk`;
- the same two user turns were present byte-for-byte;
- follow-up input was visible.

The original tab's history contained both identities as separate entries with the same title: the stored identity was current in the original tab, while the rewritten identity was current in both reopened tabs. A fresh AI Mode tab exposed only ten history entries and did not expose the exact stored `data-thread-id`, so a safe exact-id history selection was unavailable. No title-based or transcript-only identity fallback was used.

This is not a short provisional mismatch. Google appears to restore or fork the transcript under a different thread identity. `checkWritable` fails closed as designed, but the current URL identity model cannot satisfy FR-4.5/FR-4.7 on the observed live page.
